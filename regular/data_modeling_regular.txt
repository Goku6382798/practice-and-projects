
# Data Modeling Preparation Guide - Regular Study

## 1. Introduction to Data Modeling
- What is Data Modeling? → Process of designing data structures and relationships.
- Types of Models:
  - **Conceptual Model** → High-level, entities and relationships (business view)
  - **Logical Model** → Attributes, primary keys, foreign keys, normalization
  - **Physical Model** → Actual database schema (tables, indexes, constraints)

## 2. Entity-Relationship Diagrams (ERDs)
- Entities, Attributes, Relationships
- Cardinality: One-to-One, One-to-Many, Many-to-Many
- Keys: Primary Key, Foreign Key, Candidate Key, Composite Key

## 3. Normalization
- Purpose: Eliminate redundancy, maintain consistency.
- Forms:
  - **1NF (First Normal Form):** Atomic values, no repeating groups
  - **2NF:** 1NF + no partial dependency (on part of composite key)
  - **3NF:** 2NF + no transitive dependency
  - **BCNF (Boyce-Codd Normal Form):** Stronger version of 3NF
- Advantages: Data integrity, less redundancy
- Disadvantages: More joins, may reduce performance

## 4. Denormalization
- Definition: Intentionally introducing redundancy for performance gains.
- Use cases: Reporting systems, OLAP systems
- Trade-offs: Faster reads, slower writes, risk of inconsistency

## 5. Star Schema
- Central **Fact Table** with **Dimension Tables**
- Simple, widely used in data warehousing
- Example: Sales fact table (sales_amount, date_id, product_id, customer_id)

## 6. Snowflake Schema
- Extension of Star Schema with normalized dimensions
- Reduces redundancy, but more complex joins

## 7. Fact and Dimension Tables
- Fact Table: Quantitative data (metrics, measures, foreign keys to dimensions)
- Dimension Table: Descriptive attributes (who, what, where, when)
- Grain: Level of detail in a fact table (daily sales, per transaction)

## 8. Surrogate Keys vs Natural Keys
- Surrogate Key: Artificial key (auto-increment ID)
- Natural Key: Key from business data (SSN, email, etc.)
- Trade-offs: Surrogate keys ensure uniqueness and flexibility

## 9. Slowly Changing Dimensions (SCD)
- Managing changes in dimension attributes over time.
- Types:
  - **SCD Type 0:** Retain original value (no change)
  - **SCD Type 1:** Overwrite old data (no history)
  - **SCD Type 2:** Add new row with versioning (historical tracking)
  - **SCD Type 3:** Add new column for limited history
- Example: Customer address change → preserve history or not?

## 10. Change Data Capture (CDC)
- Process of identifying and capturing changes in source data.
- Techniques:
  - Log-based CDC (database transaction logs)
  - Trigger-based CDC
  - Timestamp-based CDC
- Used in ETL and streaming pipelines for real-time updates.

## 11. Data Lineage and Metadata
- Data Lineage: Tracking data flow from source → transformations → target
- Metadata: Data about data (schema, owners, refresh frequency)

## 12. Data Types and Constraints
- Data Types: INT, VARCHAR, DATE, JSON, etc.
- Constraints: NOT NULL, UNIQUE, CHECK, DEFAULT

## 13. Indexing
- B-Tree Index, Hash Index, Bitmap Index
- Clustered vs Non-Clustered
- Trade-offs: Faster reads, slower writes

## 14. Partitioning and Sharding
- Partitioning: Dividing large tables into smaller pieces (range, list, hash, composite)
- Sharding: Horizontal scaling by splitting data across multiple servers

## 15. OLTP vs OLAP
- OLTP: Online Transaction Processing (frequent, small transactions)
- OLAP: Online Analytical Processing (complex queries, aggregations)

## 16. Data Vault Modeling (Advanced)
- Hub, Link, Satellite structures
- Good for scalability, auditability, historical tracking

---

# Preparation Strategy
- Start with ERDs, normalization → star schema → SCD & CDC.
- Revise trade-offs: normalization vs denormalization, surrogate vs natural keys.
- Draw schemas for practice (e.g., e-commerce, banking, healthcare).
- Implement small warehouse schema (fact + dimensions) in SQL.
- Be ready to discuss design choices in interviews (e.g., why Type 2 SCD over Type 1).
