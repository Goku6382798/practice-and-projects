While creating the Fact table we will use all the Dimkeys that were created inside dim tables
FACT Table:-
Dimcustomerkey, Dimproductkey, Dimpaymentkey, Dimregionkey, Dimsaleskey, quantity, unit_price

Below is the query for more understanding:-

SELECT
 Dimcustomerkey, 
 Dimproductkey, 
 Dimpaymentkey, 
 Dimregionkey,
 Dimsaleskey, 
 F.quantity, 
 F.unit_price
FROM
 datamodeling.silver.silver_table F
LEFT JOIN
 datamodeling.gold.dimcustomers C
 ON F.customer_id = C.customer_id
LEFT JOIN
 datamodeling.gold.dimproducts P
 ON F.product_id = P.product_id
LEFT JOIN
 datamodeling.gold.dimregions R
 ON F.country_id = R.country
LEFT JOIN
 datamodeling.gold.dimpayments PY
 ON F.payment_type = PY.payment_type
LEFT JOIN
 datamodeling.gold.dimsales S
 ON F.order_id = S.order_id

STAR SCHEMA:
- Dimensions are denormalized (flattened)
- Simple structure and faster queries
- Uses more storage
- Example: One Fact table linked to denormalized dimensions

SNOWFLAKE SCHEMA:
- Dimensions are normalized (split into sub-tables)
- Reduces redundancy
- More complex joins but saves space
- Example: Product dimension split into product and category tables


NATURAL KEY:
- Comes from source system (e.g., customer_id)
- Can be messy, duplicate, or change over time

SURROGATE KEY:
- Artificial key generated during ETL (e.g., auto-increment ID)
- Stable, unique, and efficient for joins
- Used in fact tables as foreign keys


DATA LINEAGE:
- The ability to trace data’s journey from source → transformations → destination
- Helps in debugging, auditing, and impact analysis
- Tools: Apache Atlas, OpenLineage, Databricks Unity Catalog


SCHEMA EVOLUTION:
- The ability of a data model to handle changes in schema (e.g., new columns, changed data types)
- Supported in Delta Lake and Apache Iceberg
- Example: ALTER TABLE ADD COLUMN or automatic merge schema during ingestion


🧩 DIFFERENCE BETWEEN UPSERT AND MERGE

UPSERT:
- Combination of "UPDATE" and "INSERT".
- If the record already exists → UPDATE it.
- If the record does not exist → INSERT it.
- Simpler concept, not always a separate SQL keyword (depends on the database).
- Commonly used in PostgreSQL (INSERT ... ON CONFLICT), MySQL (INSERT ... ON DUPLICATE KEY UPDATE).
- Example (PostgreSQL):
  INSERT INTO customers (id, name, email)
  VALUES (1, 'John', 'john@example.com')
  ON CONFLICT (id)
  DO UPDATE SET name = EXCLUDED.name, email = EXCLUDED.email;

MERGE:
- A more powerful and flexible statement that combines INSERT, UPDATE, and DELETE in one operation.
- Matches records between a source and a target table based on a condition.
- Allows different actions for matched and unmatched rows.
- Supported in SQL Server (T-SQL), Oracle, Snowflake, and Delta Lake (Databricks).
- Example (Databricks SQL / Delta Lake):
  MERGE INTO target_table AS T
  USING source_table AS S
  ON T.id = S.id
  WHEN MATCHED THEN
    UPDATE SET T.value = S.value
  WHEN NOT MATCHED THEN
    INSERT (id, value)
    VALUES (S.id, S.value);

KEY DIFFERENCES:
| Feature | UPSERT | MERGE |
|----------|---------|-------|
| Purpose | Update or insert single record set | Compare two datasets (source vs target) |
| Flexibility | Limited (update or insert only) | Can UPDATE, INSERT, DELETE, or even do nothing |
| Syntax | Usually DB-specific (ON CONFLICT, ON DUPLICATE KEY) | Standard ANSI SQL syntax |
| Use Case | Small updates or single table operations | Large table synchronization and data warehouse loads |
| Support | PostgreSQL, MySQL | Databricks (Delta), SQL Server, Snowflake, Oracle |

In summary:
- Use UPSERT for **simple insert-or-update logic**.
- Use MERGE for **complex synchronization between two tables**.



BEST PRACTICES:
- Keep dimension tables small and descriptive
- Use surrogate keys instead of natural keys
- Use consistent naming conventions (dim_*, fact_*)
- Maintain incremental pipelines
- Apply SCD Type 2 for history tracking
- Ensure data quality checks between Bronze → Silver → Gold layers
